# Translation layer study: x86_64 <-> arm64 (a Rosetta 2 for ClokeOS)

Status: study plus a tiny proof (`xlat/`), 2026-10-29. Goal: run foreign-architecture programs in both directions
(x86_64 on arm64, arm64 on x86_64) for all three binary kinds: Mach-O, Windows PE (through Wine), Linux ELF (through `tux`).
Figures marked *(est.)* are estimates from public experience with these projects, not measurements on ClokeOS.

## 1. Facts about the platform (PureDarwin XNU 20.5, no kernel patch)

Measured in the arm64 VM (HVF, `xlat/jitprobe`, `xlat/x64run`):

| Question | Result |
|---|---|
| Page size | 16 KiB (`hw.pagesize`). x86_64 programs assume 4 KiB, so `mmap`/`mprotect` granularity is wrong by 4x (Rosetta gets 4 KiB user maps from Apple's kernel). |
| `mmap` RWX with `MAP_JIT`, then `mprotect` RX / RWX | works. `pthread_jit_write_protect_np` and `sys_icache_invalidate` link and run; generated code executes (returned 42). No entitlement or signing problem. |
| Write fault on a protected page | `SIGSEGV`/`SIGBUS` handler runs, can `mprotect` and resume. This is enough for self-modifying-code detection (write-protect translated pages), as QEMU does. |
| Address space | `MAP_FIXED` works at 8 GiB, 16 GiB, `0x7ffee0000000` (x86_64 stack), `0x7fff00000000` (dyld region) and 64 TiB. Fails at 0x1000 (below 4 GiB there is no memory for arm64 programs; a smaller `-pagezero_size` gets the process killed with SIGKILL) and at `0x7fffffe00000..` (top 2 MiB below 2^47), **so the x86_64 commpage address is not mappable**. |
| Translator image vs. guest at 4 GiB | arm64 executables are always PIE; dyld slides ours to `0x10xxxxxxx`, which is exactly where x86_64 images want to live (`0x100000000`). `-image_base`/`-no_pie` are ignored by ld for arm64. Unsolved, see section 3. |
| Running an x86_64 Mach-O directly | `zsh: bad CPU type in executable`. There is no kernel hook, so a launcher is needed. |
| CPU features | `hw.optional.arm.FEAT_FlagM/LRCPC` are not reported by this kernel (the same host CPU reports them under macOS); whether the guest CPU has them is **untested** (would need an ID-register read, which EL0 cannot do). |
| TSO | Apple's hardware TSO mode (what Rosetta uses) is switched by the kernel for the thread; no user-space or HVF-guest path is known. **Not available** without a kernel patch, and not tested. |

Other constraints known from the code base: `tux` already rewrites `syscall`/`svc` instructions and runs a signal-based
trap; PureDarwin has no SysV shm; one CPU core by default; the x86_64 guest image runs under TCG (slow), so x86_64-host work
can only be validated on real PCs or slowly in QEMU.

Notable simplification: **Darwin BSD system call numbers and LP64 structure layouts are identical on x86_64 and arm64**
(`x64run` passes `write`/`exit` straight to the host `syscall()`). Mach-O x86_64 -> arm64 needs no struct conversion, unlike
Linux (x86_64 and arm64 differ in call numbers, `stat`, `ioctl`, `sigaction`, `ucontext`), where `tux/nr.h` and `sys.c` would
have to be made guest-ABI-aware instead of host-arch-aware (today `#ifdef TUX_ARM64/TUX_X86_64` select the host's ABI).

## 2. Options

| Option | License | Effort *(est.)* | Speed *(est.)* | Fits ClokeOS? |
|---|---|---|---|---|
| **A. QEMU TCG as a library** (Unicorn 2.x; QEMU's `linux-user` and `bsd-user` do not build for Darwin hosts and have no Darwin guest ABI) | GPL-2.0 (check upstream before shipping; QEMU parts are GPL) | Low for a first run (loader + syscall layer around a CPU core: weeks); no thread story (one engine per thread, shared memory by `uc_mem_map_ptr`) | 5-20x slower than native; fine for tools, poor for GUIs | Both directions from one code base, all ISAs, good as **correctness oracle** and as the arm64->x86_64 direction. | **B. Unverified whether either builds on Darwin. |
| **C. Own translator** (Rosetta-style: block JIT x86_64->arm64 with lazy flags, 1:1 guest memory, syscall pass-through for Darwin; AOT cache later) | own code | Very high: decoder + ~500 integer ops + SSE2 + x87 + flags + signals + threads: months to run busybox-class programs, long tail for Mac apps | 60-90% of native when mature | Full control, no license issue, can exploit Darwin simplicity (Mach-O needs no syscall conversion). Reverse direction (arm64->x86_64) is a second, smaller back end. |
| **D. Hook point** | - | - | - | See below. |

Hook points (independent of the translator choice):
1. **Launcher** (`xrun prog`): works today, no kernel patch; used by Fundus/Terminal via a wrapper like `tux-run`.
2. **`DYLD_INSERT_LIBRARIES` interposer on `execve`/`posix_spawn`** in the shell and desktop processes (children of a translated program are handled by the translator's own `execve`): makes foreign binaries "just run" from native programs. Needs per-process insertion (launchd/zsh startup), no kernel patch.
3. **Kernel `exec_mach_imgact` fallback** (try the translator on `EBADARCH`, plus `binfmt`-like ELF/PE detection): clean and the only fully transparent option; needs a rebuilt or binary-patched kernel (`kcfix.py` shows binary patching is possible but fragile).
4. **`tux`**: already the loader for Linux ELF; a foreign ELF would swap "jump into the program" for "run it in the translator" and keep `sys.c`.

Wine/PE: the cheapest Windows-on-arm64 route needs **no new Wine build**: run the x86_64 `wine` (a Mach-O, already in the x86_64 image) inside the Mach-O translator, so wine, its x86_64 PE side and the Windows program are all translated together. Costs: speed, and Wine's own use of `%gs`/signals/address-space reservation must work in the translator. The alternative (Wine arm64 + FEX's `libwow64fex.dll`, "Hangover" style) is faster but needs an arm64 Wine build for PureDarwin (Nix on Linux, ~60 GB) first.

Dynamic Mach-O (the real target, apps and Wine): needs dyld and libSystem **of the guest architecture** in the tree. The x86_64 system libraries exist in the x86_64 image; for an arm64 image they have to be shipped (e.g. under `/usr/lib/x86_64`), plus an emulated commpage (not mappable at the x86 address, see above: the translator must intercept those loads or patch libSystem).

## 3. Recommendation and order

Decision: **A first as the oracle and the quick start, C as the product** (B is dropped unless a Darwin build of its core turns out to be cheap).

Order:
1. (done here) Probe the platform: JIT, page size, address space. Result above: JIT and signals work; 16K pages, no commpage address and the PIE slide at 4 GiB are the real issues.
2. **Smallest useful next step**: `xlat/x64run` grown into a small x86_64 *interpreter* for static Mach-O (ClokeOS-built static programs, `-nostdlib` or a static libc), with the launcher `xrun`. It needs no JIT, tests the loader, syscall pass-through, stack/auxv and the 16K-page problem, and becomes the reference for the JIT (differential testing against it and against Unicorn).
3. Solve the three platform problems: guest memory model (1:1 with the translator loaded out of the way, e.g. a launcher that re-executes until the dyld slide misses `[4 GiB, 4 GiB + guest)`, or a software `base + addr` offset in the JIT), 4 KiB emulation on 16 KiB pages (split guard pages, track guest protections in a table, `mprotect` only at 16K), commpage emulation.
4. Block JIT for x86_64 -> arm64 (lazy flags with `FlagM` where present, plain `LDR/STR` without TSO; add `LDAR/STLR` or `DMB` only for multi-threaded programs or after measuring), then SSE2/x87, then threads and signals.
5. Dynamic x86_64 Mach-O (dyld + libSystem of the guest ISA), then x86_64 Wine inside it (Windows on arm64), then foreign ELF in `tux` (guest-ABI tables in `nr.h`/`sys.c`).
6. Reverse direction (arm64 -> x86_64): start with option A (Unicorn/TCG) behind the same loader/syscall layer; replace by a small arm64 decoder + x86_64 emitter only if speed demands it. Note arm64 programs of the Mac world will need arm64 Darling frameworks on x86_64 images.
7. Kernel exec hook as the last convenience step.

## 4. What the proof shows (and does not)

`xlat/build.sh` builds: `jitprobe` (platform probe), `x64run` (about 30-instruction x86_64 interpreter: thin Mach-O loader,
`LC_UNIXTHREAD`/`LC_MAIN`, register file, flags for add/sub/cmp/xor, push/pop/call/ret/jmp/jz/jnz, modrm/SIB/RIP-relative,
`syscall` -> host `syscall()` with Darwin class 2 numbers) and `hello-x64` (static x86_64 Mach-O, prints three lines, exit code 7).

Tested in the arm64 VM (ClokeOS 2.5 desktop image copy, QEMU + HVF): `./hello-x64` -> `bad CPU type in executable`;
`./x64run hello-x64` -> three lines, exit code 7 (same as the host Mac). `jitprobe` output as in section 1.

Option A, second round (user approved the download; Unicorn 2.1.4, `COPYING` is GPL-2.0, 27 MB source): `xlat/ucrun` is the
same loader with Unicorn as CPU core. It builds for Darwin 20 arm64 without changes (static, linked against the image's libSystem,
3 MB) and **runs the same hello in the arm64 VM with the same output and exit code 7**. So QEMU's TCG, including its `MAP_JIT`
code buffer, works on PureDarwin without a kernel patch. Unicorn keeps guest memory in its own address space with 4 KiB pages,
so the 16 KiB host page, the missing pagezero range and the PIE slide at 4 GiB do not matter for it (they still do for an own 1:1 JIT).
Still unknown for Unicorn: speed (not measured), threads, dynamic Mach-O, guest memory management by syscalls (`mmap`).

Not tested: x86_64 host side (the proof is arm64-only; the reverse direction is not started); any dynamic Mach-O, threads,
signals, SSE/x87, TSO, `FlagM`/`LRCPC` availability, the 4 KiB emulation, the commpage, performance of any of it, building
Unicorn or Box64/FEX on Darwin, the claimed licenses and speeds (from memory/public experience, not re-verified here).

## 5. Progress after the first round (2026-10-29)

**Static x86_64 Mach-O now runs through `xlat/ucrun`** (Unicorn as CPU core, arm64 build against the image's libSystem):
- Kernel-style initial stack (argc, argv, envp, apple), `LC_UNIXTHREAD` entry, fat files (x86_64 slice picked).
- Darwin syscall layer with a small table (pointer in/out/path marshalling, `mmap` anonymous and file, `munmap`, `read`, `write`, `open`, `stat64`/`fstat64`, `lseek`, `pread`, `gettimeofday`, `getentropy`, ids ...), errors reported the x86_64-Darwin way (CF + errno). Structures need no conversion. `mprotect` is a no-op (guest memory stays RWX), Mach traps (class 1) and everything else answer ENOSYS and say so.
- `xlat/t-sys.c` is a freestanding x86_64 test (syscalls, mmap, SSE doubles, file read of its own header, stat, ENOENT, getpid, a 4M sieve). It passes on the host Mac and in the arm64 VM.

**Speed** (sieve of 4M plus 31 syscalls; short run, includes TCG warm-up): x86_64 binary natively under Rosetta on the host Mac 0.015 s; `ucrun` on the host 0.25-0.28 s; `ucrun` in the arm64 VM (HVF, same M-series CPU) 0.33 s. So Unicorn is **about 17-20x slower than Rosetta** here, roughly what plain TCG gives. Fine for command-line tools, too slow for GUIs and Wine. Only one program, no statistics; the VM figure also carries the PureDarwin kernel's overhead.

**Exec hook** (`xlat/exechook.c` -> `libxlat-exec.dylib`, loaded with `DYLD_INSERT_LIBRARIES`): interposes `execve`, `execv`, `execvp`, `posix_spawn`, `posix_spawnp`; a Mach-O without a host slice but with an x86_64 slice is started through `$XLAT_UCRUN` (default `/usr/bin/ucrun`). In the VM, `zsh -c ./hello-x64`, `sh` with a PATH lookup and Python's `os.execv` all ran the x86_64 program (exit code 7 kept); without the library zsh says `bad CPU type in executable`. Limits: only processes that load the library (not automatic yet: nothing sets `DYLD_INSERT_LIBRARIES` in the image, deliberately, because it affects every process); libc-internal `exec*`/`system`/`popen` paths that do not go through these five symbols are not caught; no Fundus/Terminal double-click entry yet. The real fix remains a kernel `exec_mach_imgact` fallback.

**Dynamic x86_64 programs now run (2026-10-29, second session step).** `ucrun` loads the *guest's own* `/usr/lib/dyld` (x86_64, from PureDarwin's x86_64 image) the way the kernel would, builds the kernel-style initial stack (`mach_header*`, argc, argv, envp, apple), and lets dyld load the program and the x86_64 `libSystem.B.dylib` (+ `libdyld`, `libobjc.A`, `libc++abi`) from `XLAT_ROOT` (`xlat/xroot.sh` extracts them; nothing goes into the repository). A dynamic C program with `printf`, `malloc`, `puts` (`xlat/hello-dyn.c`) prints the right output and exits with code 5, **on the host Mac and in the arm64 VM** (0.15 s start to exit in the VM, 142 syscalls). It needed, found by running and tracing:
- the commpage at `0x7fffffe00000` (signature, version, ncpus, memory size, the nanotime block that `mach_absolute_time` spins on until its generation is non-zero),
- Mach traps answered with fixed port names (`task/thread/host_self`, `mach_reply_port`, `mach_vm_allocate/deallocate/map` onto the guest allocator, `mach_port_allocate`, `mach_timebase_info`), `thread_set_tsd_base` -> `%gs` base,
- `mach_msg` served as a tiny MIG server for exactly what libSystem's initializer asks: `host_info` (basic and priority info), `host_get_clock_service`, `task_get_special_port` (bootstrap = MACH_PORT_NULL, there is no launchd), `semaphore_create`,
- BSD calls: `sysctl` (answers describe the *host*, so e.g. `hw.machine` says arm64: a known inconsistency), `getattrlist`, `fcntl` (`F_CHECK_LV` succeeds, `F_ADDFILESIGS*` -> ENOTSUP, `F_GETPATH`), `stat`-family through libc, `csrctl`, `bsdthread_register`, `thread_selfid`, `shared_region_check_np` (EINVAL = no shared cache), `getrlimit`, signal calls as no-ops. The x86_64 `libSystem` here is a monolithic PureDarwin build, which is why so few libraries are needed.
Not working or not tried: threads (`pthread_create` -> `bsdthread_create`/Mach threads; needs one Unicorn context per guest thread), signals (all signal calls are no-ops, so handlers never run), `fork`/`execve` inside the guest, `mach_msg` to anything except the five calls above (no bootstrap/launchd, so no XPC, no CoreFoundation services, no window server), C++ (libc++ is not extracted yet), Objective-C/CoreFoundation programs, `mprotect` (guest memory is always RWX), files mapped shared, `fsgetpath` (427) and several other calls that return ENOSYS with a message on stderr. Wine and GUI programs are therefore still a long way off; the next blockers are threads and signals, then `fork`/`exec` and sockets.

**Not done: x86_64 Linux ELF through `tux`.** `tux/nr.h` and `tux/sys.c` select the *host* ABI with `#ifdef TUX_ARM64/TUX_X86_64`; for a foreign ELF they must select the *guest* ABI (numbers, `stat`, `sigaction`, `ioctl`) and read/write registers through a context struct instead of the signal `ucontext`, with `ucrun`'s `UC_HOOK_INSN SYSCALL` as the entry. That edits files of the `tux` work stream (session `clokeos-linux-programme`), so it was not started; it should be agreed with that session first.

**JIT/AOT plan (replaces Unicorn for speed).** Order of speed-ups, each verifiable against Unicorn as oracle on the same test programs: (1) own basic-block translator x86_64->arm64 for the integer subset with lazy flags, translated blocks cached in a `MAP_JIT` buffer and chained (what `x64run`'s decoder becomes); expected 3-6x faster than TCG *(est.)*; (2) SSE2/x87 added, so libc/libm run; (3) persistent AOT cache keyed by file hash + page content (translate at first run, store beside the binary, as Rosetta does in `/var/db/oah`); (4) 1:1 guest memory and syscall pass-through without copying, once the load-address problem of section 1 is solved; (5) multi-threading, with `LDAR/STLR` for shared accesses unless TSO is available. Until (1) exists, Unicorn is the shipped translator.

**Tested only in the arm64 VM / on the host Mac:** everything above. Nothing was run on x86_64 hosts (no arm64 -> x86_64 direction, no x86_64 build of `ucrun` or the hook).

## 6. Threads (work in progress) and a long-term target: Logic Pro

**Threads work (basic pthreads), 2026-10-29.** `xlat/hello-thr.c` (4 threads, 20000 mutex-protected increments each, `pthread_join`, return values) prints the right result **on the host Mac and in the arm64 VM** (0.5 s / 0.9 s). How it works in `ucrun`: guest memory is host memory mapped into every Unicorn engine with `uc_mem_map_ptr`; each guest thread has its own engine, created inside its own host thread (Apple's JIT memory is bound to the creating thread: creating the engine in the syscall hook and running it elsewhere crashed with EXC_BAD_ACCESS on the host); a ticket lock (GIL) lets only one engine run at a time because Unicorn's memory map is not safe to change while another engine runs; the lock is released around blocking calls (`read`, ulock/psynch waits) and after a time slice (1 s). `bsdthread_register` is parsed (libpthread's registration block: TSD offset 0xe0, mach-thread-self slot 0x18, relative to the TSD base), `bsdthread_create` starts a thread like the XNU kernel (entry from registration, `rsp`, `rdi`=pthread, `rsi`=thread port, `rdx/rcx`=func/arg, `r8`=stack, `r9` flags with `TSD_BASE_SET` = 0x10000000, `IA32_GS_BASE = pthread + tsd_offset`, port written into the TSD slot), `bsdthread_terminate` marks the thread's port dead, and `__ulock_wait/wake` implement `pthread_join` (UL_UNFAIR_LOCK waiters are released when the owner port is dead). Misaligned stacks showed up as an `int3` in `dyld_stub_binder` (lazy binding), which is how the first fault was found.
Known limits: **psynch is not implemented** (`__psynch_mutexwait` sleeps 20 us and returns EINTR, `mutexdrop` is a no-op): a contended `pthread_mutex` livelocks, which is why time slices are long (1 s) so that threads normally switch only at blocking calls; condition variables (`psynch_cv*`), rwlocks and semaphores are missing; spin-waiting on a flag stalls other threads for up to a second; dead engines are never freed; signals are still no-ops. Condition variables, Mach semaphores and contended mutexes were added later, see sections 9 and 10.

**Logic Pro 12.3 (user's goal, checked 2026-10-29 from `Logic Pro 12.3.pkg`, nothing installed or kept).** The package installs `/Applications/Logic Pro.app` (1.7 GB payload); the launcher `Contents/MacOS/Logic Pro` and `Logic.framework` (86 MB) are **universal (x86_64 + arm64)**, `LSMinimumSystemVersion` is 15.6. So the arm64 slice could run natively on an arm64 ClokeOS and the x86_64 slice through the translator, but the real obstacle is not the CPU: `Logic.framework` links about 45 system frameworks (AppKit, SwiftUI, Combine, Metal, MetalKit, CoreAudio, AudioToolbox, AudioUnit, CoreMIDI, AVFoundation, AVFAudio, CoreMedia, CoreVideo, WebKit, ScreenCaptureKit, StoreKit, Accelerate, Security, ...) plus the Swift runtime (`libswiftCore` and about 30 overlay libraries), `libxar`, `libsqlite3`, `libxml2`. ClokeOS has none of Apple's frameworks (Darling's AppKit is partial, no SwiftUI/Metal/CoreAudio/AVFoundation/WebKit), no audio stack, no launchd/XPC services (AU hosting uses XPC), no code-signing/entitlement checks, and the app needs macOS 15.6 API behavior. Realistic reading: this is a very-long-term goal that depends on the whole Mac-app layer (Darling frameworks, a CoreAudio on top of the guest's audio driver, Metal on top of a GPU driver), not on the translation layer alone. A useful intermediate checkpoint would be to get its small pieces (e.g. the `MACore` or `LogicAppFramework` dylibs loading under `ucrun` or natively) and to track which Apple symbols are missing with `otool -L`/`nm -u` against Darling's exports.

## 7. Real x86_64 programs from PureDarwin's own image (2026-10-29)

`xlat/xroot.sh` also extracts `/bin/echo`, `cat`, `uname`, `wc`, `true` and `toybox` from the x86_64 image. Unmodified, they run through `ucrun` **in the arm64 VM** (and on the host): `echo`, `cat`, `wc`, `uname -a` (`hw.machine` is overridden to `x86_64`; the rest of `uname` still describes the arm64 host), and `toybox` as `ls -l`, `find`, `sort`, `sed`, `date`. Getting `ls`/`find` to work needed `getdirentries64`, `fstatat64`, `readlinkat`, `statfs64`/`fstatfs64`, `umask`. With the exec hook, `zsh -c "$R/echo ...; $R/cat file"` runs the x86_64 binaries (`DYLD_INSERT_LIBRARIES=libxlat-exec.dylib`, `XLAT_UCRUN`, `XLAT_ROOT` set). Quirk: the guest file system is `XLAT_ROOT` first and the host second, so the guest sees the extracted x86 `/usr/lib` (a deliberate overlay, like `tux`'s `/TUX`). Still missing for general programs: `fork`/`execve` and signals inside the guest, `psynch` (see section 6), sockets, `kqueue`, `poll`/`select`, terminal ioctls (answered ENOTTY), and any Mach service.

**Processes (same day).** Guest `fork`/`vfork` is a host `fork` (guest memory is private anonymous host memory, so it is copied; child gets `rdx = 1` as on Darwin), `execve` re-executes `ucrun` for x86_64 Mach-O targets and the kernel for everything else (arm64 programs, `#!` scripts), `wait4`, `pipe`, `dup2`, `chdir`/`fchdir`, `rename`, `symlink`, `kill` and process-group calls are passed through. Result, in the arm64 VM and on the host: `toybox sh -c "cd d; ./find . | ./sort; uname -m; echo fertig"` (an x86_64 shell starting x86_64 `find` and `sort` in a pipe, then `uname`, `echo`) prints the right output. Limits: `fork` of a process with several guest threads only keeps the calling thread; signals still do nothing (so `SIGCHLD`, `SIGPIPE`, job control and `^C` are not emulated); `posix_spawn` (syscall 244) was added later, see section 11; `sh` here is toybox's, bash/zsh were not tried.

## 8. Signals (2026-10-29)

`ucrun` now emulates BSD signals for x86_64 guests. `sigaction` (guest handler + libSystem's `__sigtramp` trampoline + flags/mask), `sigprocmask`/`__pthread_sigmask`, `sigpending`, `sigsuspend`/`pause`, `sigaltstack` (ignored), `sigreturn`, `kill`/`__pthread_kill`, `alarm`, `setitimer`/`getitimer`. Real signals (`kill`, `alarm`, `SIGCHLD` ...) are caught by a host handler that only marks them pending and asks the engines to stop; delivery happens between two time slices in the guest thread: the register file (16 GPRs, XMM0-15, flags, rip) is saved, a frame (zeroed `siginfo` with signo and fault address, a zeroed `ucontext`) is built below the red zone and execution jumps into the guest's own `__sigtramp`, which calls the handler and `sigreturn`; `sigreturn` restores the saved state (the guest's `ucontext` is ignored, so handlers cannot change the interrupted context). Guest faults become signals when the guest has a handler: unmapped/protected access -> `SIGSEGV` (with the address), `div`/`idiv` exception -> `SIGFPE`, `ud2`/invalid -> `SIGILL`, `int3` -> `SIGTRAP`; without a handler the program ends with the Unicorn error message as before. The libc `*_nocancel` syscall variants (`wait4_nocancel` etc.) are mapped to the plain ones (without that, `waitpid` silently failed).
Tests (`xlat/hello-sig.c`, `xlat/hello-sig` binary built by `build.sh`): `signal`+`raise`, `SA_SIGINFO`+`kill(getpid())` with `si_signo`, blocking with `sigprocmask` (pending until unblocked), `alarm`+`pause`, `SIGCHLD` after `fork`/`waitpid`, `SIGSEGV` (NULL read) and `SIGFPE` (divide by zero) caught with `siglongjmp`; and an asynchronous `setitimer` signal into a tight loop (`/tmp/asig`-style test, five hits). All pass on the host Mac and in the arm64 VM, together with the earlier tests (static, dynamic, threads, pipeline).
Findings worth keeping: (1) after the `syscall` hook returns, Unicorn advances `rip` by the length of the instruction (2 bytes) even if the hook wrote `rip` and stopped the engine: `sigreturn` therefore passes the resume address through the thread record and `run_engine` applies it after `uc_emu_start` returned; (2) `sigset_t` bit n is signal n+1; (3) `_longjmp` calls `sigreturn(NULL, UC_RESET_ALT_STACK)`, which is not a handler return; (4) XMM registers must be saved or an asynchronous signal corrupts interrupted `memcpy`-style code.
Limits: one signal mask for the whole process (not per thread), process-wide signal delivery to whichever thread is scheduled, `SA_RESETHAND`/`SA_ONSTACK`/alternate stacks and `ucontext` modification are not supported, real-time or stop signals (`SIGSTOP`, `SIGTSTP`, job control, `^C` on a terminal) are host-default, and `sigaction` flags other than `SA_RESTART`, `SA_SIGINFO`, `SA_NODEFER` are ignored.

## 9. Condition variables, semaphores, sleeping (2026-10-29)

Added to `ucrun`: `__psynch_cvwait` (with absolute or relative timeout; `sec`/`nsec` are the 7th and 8th syscall arguments and live on the guest stack at `rsp+8/+16`), `__psynch_cvsignal`, `__psynch_cvbroad`, `__psynch_cvclrprepost`; Mach semaphores (`semaphore_create`/`destroy` as MIG messages 3418/3419 returning unique port names, traps `semaphore_signal/signal_all/wait/wait_signal/timedwait`); and `__semwait_signal` (423/334), which is how libc implements `usleep`/`nanosleep`/`sleep` (before, it returned immediately, so every `usleep` loop spun: 145,000 calls in a test). All waits release the global lock, wake early when a signal is pending (EINTR / `KERN_ABORTED`), and honour timeouts (`ETIMEDOUT` / `KERN_OPERATION_TIMED_OUT`).
This is a deliberately simple emulation: one FIFO queue keyed by the condition variable's address and a flag per waiter, not the kernel's `lgen`/`ugen`/`sgen` counters. libpthread's counters therefore drift (it gets `updateval = 0`), which is harmless for the tested uses but means `pthread_cond_destroy` bookkeeping and "signal with no waiter" races are not faithful; it relies on guest threads switching only at blocking calls (no preemption inside user code). **Still missing:** contended `pthread_mutex` (psynch mutexwait/drop, the library expects the kernel to hand the lock over and return an update value), `pthread_rwlock` (`psynch_rw_*`), `pthread_barrier`/`dispatch` primitives that need `kevent`/workqueues, `os_unfair_lock` contention beyond `__ulock_wait` (works), and real-time thread policies.
Test: `xlat/hello-cv.c` (bounded-queue producer/consumer with `wait`/`broadcast`, three waiters woken by one `broadcast`, `pthread_cond_timedwait` timing out after 100 ms, a Mach semaphore waited on by a thread and signalled by main, `semaphore_timedwait` timing out) passes on the host Mac and in the arm64 VM, together with the static, dynamic, thread, signal and asynchronous-timer tests.

## 10. Contended mutexes via ulock; rwlocks still open (2026-10-29)

The pthread sources of PureDarwin (`src/Libraries/libSystem/pthread/src/pthread_mutex.c` and the kernel side `src/Kernel/Extensions/pthread/kern_synch.c` in the local PureDarwin source tarball, already downloaded) show two mutex back ends: the classic psynch one, where the kernel keeps per-mutex wait queues with sequence words (`mgen`/`ugen`, K/E/W bits, prepost counts, owner hand-over: about 500 lines of kernel logic to port), and a **`__ulock`-based one** (`_pthread_mutex_ulock_lock_slow`, os_unfair_lock style) that libpthread selects when the environment variable `PTHREAD_MUTEX_USE_ULOCK=1` is set. `ucrun` now adds that variable to the guest environment (unless set) and implements `__ulock_wait`/`__ulock_wait2`/`__ulock_wake` closely enough for it: per-address FIFO wait queues, the value compared only on entry (32 or 64 bit), wake by `ulock_wake` (one or `ULF_WAKE_ALL`), by the death of the owner thread (`UL_UNFAIR_LOCK` as used by `pthread_join`), timeout or pending signal, and the **count of remaining waiters as the return value**, which libpthread turns into the WAITERS bit (returning 0 there would strand other waiters), errors as `-errno` when `ULF_NO_ERRNO` is set. Result: `xlat/hello-mtx.c` (6 threads incrementing under one mutex with `usleep` inside the critical section and an overlap detector, a recursive mutex taken twice by 4 threads, `trylock` on a held mutex) passes on the host Mac and in the arm64 VM; all earlier tests still pass. Honest caveat: the threads are scheduled cooperatively, so the test produced only a few real waits (two `__ulock_wait` calls in a run); mutual exclusion and recursion are verified, heavy contention is not stress-tested. Programs that call the psynch mutex path anyway (process-shared mutexes, an explicit `PTHREAD_MUTEX_POLICY` request that bypasses the default, or an x86_64 libSystem without the ulock variant) still hit the old `psynch_mutexwait` stub (sleeps 20 us, returns EINTR) and can livelock.
**rwlocks (`pthread_rwlock`) are not done.** libpthread has no ulock variant: `__psynch_rw_rdlock/wrlock/unlock/unlock2/longrdlock/yieldwrlock` (syscalls 306-311) take the L/U/S sequence words and expect the kernel to return exact `updatebits` (grant bits, `EBIT`/`KBIT`/`MBIT` overlap handling) that `_pthread_rwlock_updateval` merges into the lock; an approximation would corrupt the lock state. The honest options are a faithful port of the rw part of `kern_synch.c` (roughly 1000 lines with the `ksyn_queue_*` helpers, adapted to `ucrun`'s waiter lists) or leaving rwlocks to the cooperative scheduler, which makes them work as long as no thread blocks while holding one (uncontended read/write locks never reach the kernel). Not tested.

## 11. posix_spawn (2026-10-29)

`ucrun` implements the `__posix_spawn` syscall (244): `pid_t *pid, path, struct _posix_spawn_args_desc *adesc, argv, envp`. The descriptor's first two pairs are used (attributes: `psa_flags`, `psa_sigdefault`, `psa_pgroup`; file actions). The struct layouts come from XNU's `bsd/sys/spawn_internal.h` (in the local PureDarwin source tarball): a file-action record is 1040 bytes (`type`, `fd`, then for `PSFA_OPEN` `oflag`, a 16-bit `mode` and the path starting at offset 6 of the union, **not** 8: that padding assumption was the one bug), actions supported are open, close, dup2, inherit (no-op), chdir, fchdir; attributes supported are `POSIX_SPAWN_SETEXEC` (replace the process, no fork), `SETPGROUP` and `SETSIGDEF`; everything else (`RESETIDS`, `SETSIGMASK`, `START_SUSPENDED`, `CLOEXEC_DEFAULT`, ports, personas, QoS) is ignored. The path is checked with `access(X_OK)` first so a missing program yields `ENOENT` from `posix_spawn` itself, as with the kernel. The child is a host `fork` followed by the same `execve` path as the guest's `execve` (x86_64 targets re-run `ucrun`, arm64 programs and scripts go to the kernel). `libc`'s `posix_spawnp` (PATH search) works on top of it.
Test `xlat/hello-spawn.c`: redirect a child's stdout into a file through `addopen`, a pipe with `adddup2`/`addclose` read back from the parent (`uname -m` prints `x86_64`), `ENOENT` for a missing program, a child's exit status; passes on the host Mac and in the arm64 VM together with all earlier tests (note: the test needs `$XLAT_ROOT/bin` on `PATH` for `posix_spawnp`). Shells and tools that spawn with `posix_spawn` instead of `fork`+`exec` (most modern macOS programs, `system()`, `popen()`) should now work; not tried beyond this test.

## 12. Wiring into the image (2026-10-29)

`xlat/image.sh` (called from `brand.sh` for the arm64 desktop image, skipped when the Unicorn source or the x86_64 PureDarwin image is missing) stages: `/usr/bin/ucrun`, `/usr/lib/libxlat-exec.dylib`, `/usr/bin/xlat-open` (double click in Fundus: opens `ucrun` in a terminal), `xlat.desktop` and the MIME magic for x86_64 Mach-O (`application/x-x86-macho`), the x86_64 system libraries under `/Library/ClokeOS/x86` (dyld, libSystem, libdyld, libobjc, libc++, libc++abi; 12 MB; `ucrun` uses this folder by default when `XLAT_ROOT` is not set), an `/etc/profile` block that exports `DYLD_INSERT_LIBRARIES`/`XLAT_ROOT` (so `cloakserver-start`, which sources `/etc/profile` before `xinit`, passes the hook to the whole desktop session: Fundus, Terminal, every program launched from them), and `/etc/clokeos-xlat.zsh`, which `/etc/zshrc` sources. A shell cannot load the hook after it has started (dyld evaluates `DYLD_INSERT_LIBRARIES` only at process start), so an interactive zsh without the hook restarts itself once (`exec zsh`, guarded by `XLAT_HOOKED`).
Tested first in the arm64 VM by unpacking the staged files into a clone of the 2.5 image: after `exec zsh -l`, `/tmp/x/hello-dyn` (dynamic x86_64) ran directly from the prompt with exit code 5, and Python's `subprocess` started the threaded x86_64 test through the hook. **Then with a full image:** `brand.sh` for the arm64 desktop (private `CLOKEOS_WORK`, cached CloakServer/macapps build dirs copied from another session's rig) built `clokeos-2.6-arm64-desktop.img` with the step included (`/usr/bin/ucrun`, the hook, `/Library/ClokeOS/x86`, `xlat.desktop`, the MIME and profile/zshrc changes all present in the image), it booted to the login screen and desktop, and in the real desktop session: (1) the Terminal app's zsh ran `./hello-sig && ./hello-dyn` (x86_64 programs, typed at the prompt) with the right results and exit code 5; (2) Fundus > select `hello-dyn` > Open With > "x86_64 Program" opened a Terminal window running it through `ucrun` (output and "exited normally with status 5" visible). **Does not work yet:** Fundus does not recognise x86_64 Mach-O files by content, so a plain double click opens the "Open With" dialog (type shown: `application/octet-stream`) instead of `xlat-open`. Possible fixes: build a real `mime.cache` with `update-mime-database` during `brand.sh`, or let `xlat-open`/`tux-open` be the default for `application/octet-stream` files with the executable bit (too broad). Untested: bash, ssh logins, the long-term effect of `DYLD_INSERT_LIBRARIES` on every desktop process. `ucrun` no longer prints "not implemented" syscall warnings unless `UCRUN_WARN` (or `UCRUN_TRACE`) is set. Known quirks: the guest file system is `XLAT_ROOT` first (so `/usr/lib/libSystem.B.dylib` seen by x86_64 programs is the x86 one), the interposer covers `execve`, `execv`, `execvp`, `posix_spawn`, `posix_spawnp` only, and `uname`-style host queries still describe the arm64 kernel except `hw.machine`.

## 13. MIME database (2026-10-29)

**Cause found:** PureDarwin's glib (checked in the arm64 image and in the sysroot's `libgio`) reads **only `mime.cache`**; it does not read the text files `globs2`/`magic` that the repository had written by hand for Wine (`.exe`, `.msi`, `.dmg`) and `tux` (ELF), and the image has no shared-mime-info database at all. So none of these file associations could be detected by name or content before (`gio info` on an `.exe` gave `application/octet-stream`).
**Fix (in the repository):** `mime/build.sh` (called from `brand.sh` for the desktop) builds a real database with `update-mime-database` (Homebrew `shared-mime-info`, GPL-2.0, `brew install shared-mime-info`; the step is skipped with a notice if it is missing) from the standard `freedesktop.org.xml` plus `mime/clokeos.xml`, which defines `application/x-linux-elf` (magic `\x7fELF`, priority 90) and `application/x-x86-macho` (magic `cf fa ed fe 07 00 00 01`, priority 90) and deliberately does not make them subclasses of `application/x-executable` (so Fundus does not try to run them itself). The result (about 350 KB: `mime.cache` plus the text files) replaces `/share/mime`. Because the standard database calls `.exe` `application/x-msdownload` (with `x-ms-dos-executable` only as an alias), the Wine associations in `overlay-desktop/share/applications` now list both names.
**Second cause found (and fixed): this glib no longer reads file contents for file info.** Disassembling the image's `libgio` (`get_content_type`) shows that `g_file_query_info("standard::content-type")` now calls `g_content_type_guess(basename, NULL, 0, ...)` and returns: it only looks at the name, takes no path and never opens the file (a call trace of `open`/`read` confirmed: nothing is read). So Thunar saw `application/octet-stream` for ELF, Mach-O and extension-less scripts, whatever the database says. `g_content_type_guess` itself works when it gets data (checked in the VM: `x-msdownload`, `x-linux-elf`, `x-x86-macho`, `text/plain`, `application/gzip`).
**Fix: `libclokeos-mime.dylib`** (`mime/sniff.c`, built by `mime/build.sh` against the sysroot's glib, installed in `/usr/lib`, loaded with `DYLD_INSERT_LIBRARIES` through `/etc/profile`): it interposes `g_file_query_info`, `g_file_query_info_finish`, `g_file_enumerator_next_file` and `g_file_enumerator_next_files_finish`; when a regular file's content type is `application/octet-stream` it reads the first 4 KiB and sets the type from `g_content_type_guess(name, data)`. (Side effect: files without extension that contain text now are `text/plain`.) The inserted libraries have to survive in the session: `cloakserver-session` used to *replace* `DYLD_INSERT_LIBRARIES` with the arm64 libXcursor fix, which dropped both hooks for Thunar; it now prepends libXcursor and keeps the rest, and the xlat blocks in `/etc/profile`, `/etc/clokeos-xlat.zsh` append instead of overwrite.
**Verified with a full `brand.sh` build of the arm64 desktop image booted in QEMU:** in Fundus, selecting `hello-dyn` (x86_64) and pressing Return (the double-click action) opens a Terminal window through `xlat-open` and runs it with `ucrun` (output, exit status 5), without the "Open With" dialog; an ELF file opens the "Linux" app through `tux-open` (the test file was a fake 18-byte ELF, so `tux` exits with 127 as expected, but the association works, which it did not before). Not checked: real Linux ELF programs from the GUI, text files opening in an editor, performance of directory listings with many unknown files, the x86_64 image (the hook builds for both architectures but only arm64 was booted), mouse double click (the test used select + Return), Thunar's icons for the new types.

## 14. rwlocks and stress (2026-10-29)

**`pthread_rwlock` works in `ucrun`, contended included.** `__psynch_rw_rdlock/wrlock/unlock` (306-308) are a port of the rw part of PureDarwin's `kern_synch.c`: per-lock wait queue (`Kwq`) with a reader and a writer list sorted by the L sequence, `kwq_handle_unlock` (grant to readers up to the lowest writer, or to one writer; `KBIT/EBIT/WBIT`, counts in the upper bits), the unlock-before-arrival prepost (`find_seq_till`, `prepost.count/lseq/sseq`), the reader overlap path (`KWF_OVERLAP_GUARD`, `nextseqword`, `MBIT`), `_ksyn_check_init`/`CLEAR_REINIT_BITS` for re-initialised locks and `updatebits` returned in `rax`. Everything runs under the existing wait lock `wmx`; waiters sleep on `wcv` and leave on a signal (`EINTR`, they remove themselves from the queue, libpthread retries). Not ported: owner/turnstile (priority inheritance), pshared objects, the "interrupted wakeup" counters (a waiter that was already granted keeps its grant even if a signal is pending, so a wakeup is never lost), `kw_lowseq/highseq`. `longrdlock`, `yieldwrlock`, `downgrade`, `upgrade`, `unlock2` answer `ESRCH` like the PureDarwin kernel (neither it nor its libpthread uses them). There are no timed rwlock calls on Darwin.

**Found on the way (all fixed):**
- Commit cbb36bc had dropped the dispatch of `psynch_cv*`, `__psynch_cvclrprepost` and `__semwait_signal` by accident (`hello-cv` and every `usleep` were broken on main); restored.
- `thread_selfid` returned 1 for every thread. libpthread uses it for owner checks, so `pthread_rwlock_try*` from another thread gave `EDEADLK`, and recursive mutexes silently did not exclude each other. Now one id per guest thread.
- That exposed that recursive and error-checking mutexes use the *psynch* mutex path (only plain mutexes use `__ulock`). `__psynch_mutexwait/mutexdrop` (301/302) are now implemented for the first-fit policy (default): arrival-ordered waiters, prepost when the drop comes first. `hello-mtx` now also checks that the recursive mutex really excludes.
- Dead engines were never freed: `engs[64]` overflowed after 64 thread lifetimes and `eth[64]` filled up. Thread exit now removes the table entries and calls `uc_close`. The "thread is dead" set (for `pthread_join`) was a 256-entry array, now a growing hash set.
- `clock_get_time` (MIG 1000 on the clock ports, system and calendar clock), so `clock_gettime(CLOCK_MONOTONIC)` works.
- `__semwait_signal` slept in 10 ms steps (a `usleep(300)` took 10 ms); now 1 ms steps.

**Test `xlat/hello-rw.c`** (`build.sh`; argument = stress seconds): single-thread semantics (`tryrdlock/trywrlock`, recursion, `EBUSY`, `EDEADLK`, init with attribute); 6 readers + 3 writers with `usleep` in the critical sections, counters and overlap detectors (writers exclusive, readers shared, data invariant a == b), try variants under load, 3 try threads against one reader and one writer; waiters behind a reader / behind a writer; five signals while threads wait for the lock; then a stress phase with 12 threads for N seconds mixing rwlock, mutex with sleeping owner, bounded queue with condition variables (with `timedwait`), a 3-token Mach semaphore and short-lived threads created and joined (about 400-500 in 3 s).
**Results:** host Mac and arm64 VM (clone of the 2.5 desktop image, HVF): `hello-rw` passes (host: 6 of 6 runs of 3-5 s; VM: 4 runs), together with `hello-dyn/thr/cv/mtx/sig/spawn`. 878 rw syscalls reach the port in a 1 s run.

**Open points:**
- **Time slice (changed afterwards):** the cause of the wrong counts with short slices is Unicorn's handling of an outside stop request (found by the a64run work, section 15): it checks after every guest load/store and restarts at the *beginning* of that instruction, so `mov rax,[rax]`-style instructions can run twice. `ucrun` therefore no longer uses `uc_emu_start`'s timeout or `uc_emu_stop` from other threads: a ticker thread (and the host signal handler) only sets `stop_flag`, and a `UC_HOOK_BLOCK` callback in the running engine calls `uc_emu_stop`. Also found: thread ports were `0x2000 + nsys` while libpthread keeps flag bits in the low two bits of ulock values, so the dead-thread check missed ports that were not multiples of 4 (now `0x2000 + 4*nsys`). Result with `UCRUN_SLICE_MS=10`: `hello-thr` 6/6 correct (before 2/6), `hello-rw` 16/16 (before: hangs); at 20 ms 1 of 20 `hello-rw` runs hangs, at 2 ms 6 of 20. The residual hang was not caught (one thread waits in `ulock_wait` on the join gate of a thread port; adding log output made it disappear). The default stays 1 s; do not lower it until that is understood.
- Signals are still process-wide; the mutex port ignores the owner hint (`tid`) and the fair-share policy; the rw `kwq` entries are freed 10 s after last use (the kernel does the same), never while waiters or preposts exist.
- Not tested: more than 16 threads, rwlocks shared between processes, fork while threads wait, x86_64 hosts.

## 15. The reverse direction: arm64 programs on x86_64 (`a64run`, 2026-10-29)

`xlat/a64run.c` is the mirror image of `ucrun`: Unicorn's **AArch64** core (the same 2.1.4 source tree, built for x86_64 Darwin 20 by `xlat/build-a64.sh`, only the aarch64 target, about 2.3 MB binary linked against the x86_64 image's libSystem) plus a Darwin syscall layer. Nothing of `ucrun.c` was edited; ideas and tables were copied.
**Build trap worth remembering:** Unicorn's CMake picks the TCG back end from the *compiler's default target*, not from `CMAKE_OSX_ARCHITECTURES`. On an arm64 Mac a plain `cmake -DCMAKE_OSX_ARCHITECTURES=x86_64` yields an x86_64 library with the **arm64 code generator** (first translated block jumps into arm64 code, EXC_BAD_ACCESS). `build-a64.sh` therefore passes a compiler wrapper with a fixed `-target x86_64-apple-macos11.0`.
**Architecture.** One Unicorn engine, memory owned by Unicorn (`uc_mem_map`, always RWX; the guest sees 16 KiB pages: mmap lengths and addresses are rounded to 16 KiB). `svc #0x80` arrives as `UC_HOOK_INTR` (intno 2; `pc` is already behind the `svc`), `x16` selects the class: positive = BSD call, negative = Mach trap (`mov w16,#-3` zero-extends, so the low 32 bits are sign-extended by hand), `0x80000000` with `x3 = 2` = `thread_set_tsd_base` -> `TPIDRRO_EL0`. Errors are Carry + errno in `x0`, `fork` child `x1 = 1`, `pipe` returns the fds in `x0/x1`. Struct layouts and BSD numbers equal the host's, so the table-driven pass-through of `ucrun` works unchanged. `CPACR_EL1` is set so FP/NEON run at EL0. The loader reads thin or fat arm64 Mach-O (`LC_UNIXTHREAD` for static, dyld + `LC_MAIN` for dynamic), builds the kernel-style stack and loads the **guest's own arm64 `dyld`** from `A64_ROOT` (`xlat/xroot-a64.sh` extracts dyld, libSystem, libdyld, libobjc, libc++, libc++abi from the arm64 PureDarwin image, 10 MB; the image gets them under `/Library/ClokeOS/arm64`).
**arm64 commpage** (`0xFFFFFC000`, found by disassembling the image's libSystem): only `signature`, version, ncpu, memory size and, important, the **page shifts at 0x24/0x25/0x37 (= 14)** are filled. With them 0, `vm_page_size` became 1 and libmalloc handed out odd addresses (`ldaxr` on an unaligned lock = data abort); with `user_timebase` (0xC090) = 0 libSystem asks the kernel (`mach_absolute_time` = Mach trap -3, answered from the host clock). `gettimeofday` falls back to the syscall. `sysctl` answers for `hw.machine`, `hw.pagesize`, `hw.cputype` ... describe an arm64 machine with 16 KiB pages; everything else is the host's (so `uname -a` still prints the host kernel).
**Tests, all passing.** `xlat/a64-sys.c` (freestanding arm64 like `t-sys.c`: syscalls, mmap, FP, file read, stat, ENOENT, sieve of 4M) and `a64-hello-dyn` (dynamic, `printf`/`malloc`/`puts`, exit code 5), plus the unmodified arm64 `echo`, `cat`, `uname`, `wc`, `toybox` (`ls -l`, `sort`) and a `toybox sh` pipeline with `fork`/`execve` of arm64 children, **on the host Mac (x86_64 build under Rosetta) and in the x86_64 VM** (clone of the 2.5 desktop image, QEMU TCG). The exec hook works there too: with `DYLD_INSERT_LIBRARIES=libxlat-exec.dylib`, `zsh -c ./a64-sys` runs the arm64 program, without it zsh says `bad CPU type in executable`.
**Speed (honest numbers).** Host Mac, Rosetta + TCG: static test 0.56 s, dynamic hello 5.4 s wall (2.1 s user; almost all of it is dyld + libSystem initialisation, 2 MB of translated code). x86_64 VM (TCG inside TCG): static test 13 s, dynamic hello **89 s**, `echo` and `uname` about as long each: usable as a proof, not as a daily tool. A real x86_64 PC runs TCG natively and should be in the range of the arm64 numbers in section 5 (not measured here).
**Exec hook and image.** `xlat/exechook.c` now defaults to `/usr/bin/a64run` on x86_64 hosts (`XLAT_RUN` overrides, `XLAT_UCRUN` still works); `xlat/image.sh` stages `a64run`, the hook, `/Library/ClokeOS/arm64`, `a64.desktop` (MIME `application/x-arm64-macho`, entry in `mime/clokeos.xml`) and the same profile/zshrc blocks for the **x86_64 desktop** image (`brand.sh` now calls it for both architectures; skipped with a notice when the Unicorn source or the arm64 PureDarwin image is missing). Tested only by running `image.sh` into a scratch stage directory (file list and MIME magic checked), **no full `brand.sh` build and no boot of an image that contains it.**
**Update (processes, signals, threads, 2026-10-30).** `a64run` now has the same process and thread model as `ucrun`: `posix_spawn` (file actions, `SETEXEC`, process group; `system()`/`popen()`-style spawns work), BSD signals through the guest's own `__sigtramp` (state saved on our side, frame with `x0` = handler, `x1` = style, `x2` = signal, `x3` = siginfo, `x4` = ucontext; fault signals: unmapped access -> `SIGSEGV`, undefined instruction -> `SIGILL`, `brk` -> `SIGTRAP`), threads (one Unicorn engine per guest thread created in its own host thread, ticket lock, `bsdthread_register/create/terminate`, `TPIDRRO_EL0` = pthread + tsd offset, per-thread `thread_selfid`), `__ulock_*`, condition variables, Mach semaphores, `__semwait_signal`, and the psynch mutex and rwlock port that `ucrun` got (copied block). Tests (the unchanged `hello-*.c` files, built for arm64 by `build-a64.sh`; `hello-spawn` checks `arm64` instead of `x86_64` in a temporary copy): `hello-thr`, `hello-cv`, `hello-mtx`, `hello-rw`, `hello-spawn` pass; `hello-sig` passes except the SIGFPE check, which cannot pass on arm64 (integer division by zero returns 0 and raises no signal, also on real hardware).
**Two traps found on the way.** (1) The CPU model must be `UC_CPU_ARM64_MAX`: clang for macOS 11 emits LSE atomics (`ldadd`), the default Cortex-A57 model raises an undefined-instruction exception. (2) **Never stop a running Unicorn engine from outside** (timeout argument of `uc_emu_start`, `uc_emu_stop` from a timer or signal handler): Unicorn checks for a stop request after every guest load/store and then resets to the start of *that* instruction, so `ldr x8, [x8]` runs twice with its base register already overwritten. This showed up as random "unmapped memory" crashes in dyld, rare on the host (a few stops per run) and frequent in the slow VM (about 90 one-second stops), and reproducible at will with 1 ms slices. The fix is a `UC_HOOK_BLOCK` callback that calls `uc_emu_stop` when a flag is set (by a timer thread every slice, or by the signal handler): the check right after a block hook is exact. Stops requested from inside the `svc` hook were never affected. `ucrun` (x86_64 guests) uses the timeout argument and the same signal-wake scheme; whether Unicorn's x86 core has the same flaw was not examined here (x86 instructions with destination = base register are also non-idempotent when re-run).
**Still not done / untested.** `mprotect` (memory stays RWX), sockets, `kqueue`, `fsgetpath`, C++/Objective-C/CoreFoundation programs, arm64e, anything needing a Mach service, per-thread signal masks (one process-wide mask), `SA_ONSTACK`/alternate signal stacks, and the real x86_64 PC.

## 16. Own block JIT x86_64 -> arm64 (first version, 2026-10-29)

`xlat/jit/` is an own translator for the integer subset of x86_64, plugged into `ucrun` behind `UCRUN_JIT=1` (unset = unchanged behaviour, Unicorn only). It runs the **main thread of static x86_64 programs**; everything it cannot translate is executed by Unicorn (mixed mode). Dynamic programs, threads started by the guest, and everything else stay on Unicorn (`UCRUN_JIT=1` on a dynamic program prints a notice and uses Unicorn). Files: `jit/jit.c` + `jit.h` (decoder, translator, runtime; about 1000 lines of C), `jit/ucsync.h` (register hand-over to a Unicorn engine), `jit/ucglue.inc` (the small hook included by `ucrun.c`: run loop, syscalls, signals, faults), `jit/jtest.c` (differential tester), `jit/bench.c`, `jit/t-jit.c`, `jit/build.sh`. `xlat/build.sh` now links `jit/jit.c` into `ucrun`. Changes in `ucrun.c` are marked `// JIT`: include, `jit_on`, host memory for guest regions comes from the JIT arena, the main thread's run loop, stack/mmap base moved below the arena limit.

**Guest memory.** Guest address `a` lives at host address `a + delta`; `delta` is the start of one `PROT_NONE` reservation (16 to 256 GiB, chosen by `mmap`) that `jit_guest_alloc` opens page by page. A guest load/store is `ldr xN, [xAddr, x20]` (x20 = delta): no extra instruction, and unmapped guest memory faults in the host. The same host pages are mapped into Unicorn with `uc_mem_map_ptr`, so JIT and Unicorn share memory without copying. Consequences: guest addresses must be below the arena size, so in JIT mode the stack top is at (limit - 32 MiB) and the mmap base at limit/2 instead of the x86 locations (static programs do not care; dyld/libSystem live at `0x7fff...` and do not fit, which is why dynamic programs are not supported yet). Two platform facts found on the way: (1) **the PureDarwin arm64 kernel in the VM only has 39 bit user addresses**: `mmap` above 2^39 succeeds but the first access hangs the process (not a fault), so the window must lie entirely below 2^39 (the first design used a window at 64 TiB and hung in the VM, fine on the host); (2) the host macOS ignores fixed address hints below 4 TiB, so the window is requested with a hint at the top of the 39 bit range and accepted wherever the kernel puts it, as long as it ends below 2^39 (VM: 64 GiB at `0x7000000000`).

**Registers and flags.** The 16 guest GPRs live in host `x0`..`x15` (same numbers: rax=x0, rsp=x4 ...) for the whole run, in `JitCtx` only when the JIT code is left (syscall, fallback, miss). `x19` = ctx, `x20` = delta, `x21` = indirect jump cache, `x22`..`x25` and `x16/x17` temporaries. Flags are lazy in the host NZCV register: the translator tracks per block whether NZCV currently holds ADD-like flags (C = CF), SUB-like (C = !CF, so `jb`->`cc`, `ja`->`hi` map one to one), logic (C=V=0) or nothing (flags still in ctx). A backward liveness pass over the block drops flag computation whose result is overwritten before use (`cmp` + dead flags emits nothing); inc/dec preserve CF by saving and re-inserting the C bit; `adc`/`sbb` flip C when the state has the wrong sense. At a block exit the flags are saved normalised (3 instructions) into ctx, and the save is patched to NOPs when the already translated target block does not read flags before writing them. Not kept: PF and AF (the only consumers are `jp`/`jnp`-style conditions, which fall back to Unicorn, and BCD).

**Blocks.** Up to 48 instructions, direct `jmp` is followed, blocks are cached by guest address (65536-entry hash table), direct exits are patched to `b target` once the target exists (code cache: 48 MiB `MAP_JIT`, everything flushed when full), `ret`/indirect `jmp`/`call` use a 4096-entry inline cache in the JIT code with a miss exit to the dispatcher. Backward chained exits and indirect jumps check a pending-signal word, so asynchronous host signals get delivered inside tight loops.

**Supported (translated natively):** mov (all forms, imm, 8/16/32/64 bit incl. ah..bh and REX byte registers), lea, movzx/movsx/movsxd, add/or/adc/sbb/and/sub/xor/cmp/test (adc/sbb only 32/64 bit), inc/dec/neg/not, shl/shr/sar by immediate (flags live: 32/64 bit; flags dead: all sizes) and by `cl` (flags dead, 32/64 bit), mul/imul (1, 2, 3 operands, 32/64 bit), div/idiv 32/64 bit (fast path when rdx is the zero/sign extension and the divisor is neither 0 nor -1, otherwise the instruction runs in Unicorn, which raises the exception), push/pop (64 bit), push imm, call/ret/jmp/jcc (not the parity conditions), setcc, cmovcc (not 16 bit), cdq/cqo/cwde/cdqe, xchg (not atomic), bswap, leave, `rep`/plain movs/stos (DF=0, else Unicorn), nop/endbr64, syscall, fs/gs segment bases on memory operands. **Everything else** (SSE/x87/AVX, rotates, bt*, bsf/bsr, cmpxchg/xadd/lock, cmps/scas/lods, 16-bit push/pop, 8/16-bit mul/div, pushf/popf/cld/std, cpuid, rdtsc, ...) ends the block with a fallback: consecutive such instructions (up to 160, no branch inside) are executed by Unicorn between `[rip, end)`; registers (16 GPR, rip, eflags, gs base) are handed over both ways; XMM state never leaves Unicorn because the JIT never touches it. A host fault inside JIT code (SIGSEGV/SIGBUS handler maps the host pc back to the guest instruction) re-runs that instruction in Unicorn, which reports it exactly as before (`SIGSEGV` to a guest handler or the usual message); `syscall` goes through the unchanged `do_syscall`; guest signals are delivered through the existing `push_signal`/`sigreturn` code. Self-modifying code is not detected (the cache is flushed on `munmap` and `MAP_FIXED` over translated pages only).

**Findings about Unicorn that mattered** (all handled in `ucsync.h`/`jtest.c`): (1) `uc_emu_start(count)` and `until` are baked into translated blocks, so a block cached from an earlier run with another end runs past it: before the first fallback of each range the Unicorn blocks there are dropped with `uc_ctl_remove_cache`; (2) a CPU exception (`#DE`) in an instruction run with `until` can return `UC_ERR_OK` with `rip` unchanged, so "no progress" is treated as an exception; (3) `xchg [unaligned mem], reg` gives a wrong result in Unicorn (atomic path), so the tester only compares the register form.

**Correctness tests.** `jit/jtest` generates random instruction sequences (1-4 instructions from about 30 templates, random operand sizes, registers, memory operands with base/index/scale/disp/RIP-relative, interesting immediates, random start flags, `jcc` over one instruction), runs them once in plain Unicorn (the oracle) and once in the JIT with fallback to Unicorn, and compares 16 registers, rip, CF/ZF/SF/OF (minus flags the architecture leaves undefined after that instruction, e.g. after mul or shifts by more than 1) and a 64 KiB data area. Results: **8 x 60,000 sequences on the host Mac and 60,000 in the arm64 VM, 0 mismatches** (about 8% of sequences are skipped because Unicorn itself raises an exception, about 20% touch the fallback path). Early runs found and fixed: `movsx r16,r/m16`, `inc`/`dec` losing CF, a missing `until` for fallbacks, decoder reads past the end of mapped memory. `xlat/t-sys` (syscalls, mmap, file read, 4M sieve) passes in JIT mode; `jit/t-jit` (asynchronous `setitimer` signal into a tight loop, `kill`, rep movsb, recursion, `div`, `fork` + `wait4`) passes on the host and in the VM; `hello-x64` and the dynamic/thread/signal tests are unchanged without `UCRUN_JIT` (and run on Unicorn with it).

**Speed** (`jit/bench.c`: integer kernels, built without vectorisation; time measured inside the guest, 3 runs, ms; host = Apple M-series Mac running other sessions' VMs at the same time, so +-10 %). Reference is the same x86_64 binary natively under Rosetta 2:

| kernel | Rosetta 2 | Unicorn | own JIT | Unicorn / JIT |
|---|---|---|---|---|
| sieve 4M x10 (byte stores) | 110 | 4400 | 97 | 45x |
| fib(35) (call/ret) | 42 | 2650 | 69 | 38x |
| collatz to 1M (shifts, imul, branches) | 221 | 630 | 245 | 2.6x |
| crc32 bitwise, 2 MB | 14 | 100 | 15 | 6.7x |
| matmul 200x200 int | 3 | 60 | 6 | 10x |
| byte copy 32 x 1 MiB | 17 | 3500 | 19 | 180x |
| div/mod 6M | 7 | 30 | 9 | 3x |

So the JIT is within 0.9-2x of Rosetta on these kernels (faster on the sieve, 1.6x slower on call-heavy code) and 3-180x faster than Unicorn. In the arm64 VM (HVF, no Rosetta there, other VMs running): sieve Unicorn 10748 vs JIT 186, fib 8296 vs 207-230, collatz 2277 vs 515-535, crc 258 vs 98-105, matmul 424 vs 85-111, copy 7302 vs 111-139, divmod 104 vs 81-82 ms. Caveat: **code with SSE is slower under the JIT than under Unicorn**, because each fallback costs about 20 us (register hand-over plus `uc_emu_start`): the auto-vectorised counting loop of `xlat/t-sys` (4M bytes, SSE2/SSE4.1) takes 11-30 s with `UCRUN_JIT=1` against 0.24 s on Unicorn (the benchmark is built with `-fno-vectorize` for that reason). This is why the JIT is opt-in.

**Open points / not tested.** SSE/SSE2/SSE4 and x87 natively (needs XMM in host vector registers and the register hand-over for the remaining fallbacks; this is the next step and decides whether libc/libm code runs fast), dynamic programs (guest memory above the window: dyld at `0x7fff...`; either a second delta region for the high addresses or a table lookup), threads (other guest threads run on Unicorn engines and only switch at blocking calls; the JIT thread holds the global lock between syscalls), faster fallback (keep the register file in Unicorn across runs of unsupported instructions), rotates/bt*/cmpxchg/lock-prefixed instructions and 8/16-bit adc/sbb/mul/div natively, precise self-modifying-code detection (write-protect translated pages), PF/AF, memory ordering (plain loads/stores: no TSO, fine for one thread), 4 KiB vs 16 KiB host pages (guest `mprotect` is still a no-op, as with Unicorn), the persistent AOT cache, and the x86_64 host direction. Not run: the full image build (`brand.sh`) with the changed `build.sh` (the `ucrun` link line was checked by hand against the image's libSystem, in the way the VM binaries above were built), real hardware.
